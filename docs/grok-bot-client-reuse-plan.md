# Omega 产品复刻计划

副标题：以 Grok Bot 为完整产品参照，使用 Codex App Server 构建个人多设备办公应用

更新日期：2026-09-13

状态：实施中。核心产品底座已经落地，完整功能仍按本文清单逐项复刻。本文替代原“客户端组件复用升级计划”，沿用原文件名以保持已有链接有效。

## 1. 产品目标与完成定义

将 Omega 建设成一个具有 Grok Bot 完整产品体验的新应用：以 Grok Bot 的实际界面、信息结构和功能流程为参照，重建客户端；使用 Omega 品牌，以 Codex App Server 为主要执行后端，支持 Web、Windows、macOS 和 Android 多设备持续办公。

用户希望得到的是一个可以日常使用的“新版 Grok Bot 式 Omega”。现有 Omega 的页面结构不再决定新版设计；复用几个组件或更换皮肤不能作为本项目完成的依据。

完成标准是：功能对照清单中的目标能力都有实际入口、状态反馈、真实执行结果和验收证据；用户能够按参照产品的方式完成工作，并保留 Omega 已明确的多端同步、跨项目群组和已有会话上下文需求。

首个可用版本与完整复刻分开验收。首版跑通聊天不代表完整复刻结束；暂缓项目仍留在清单中，记录原因、依赖和后续里程碑。

## 2. 产品参照与调查方法

参照来源为本地 `../grok-bot-0.18-reconstructed` 仓库、能够运行的重建客户端，以及可验证的 Grok Bot 0.18 原版界面与行为。原版行为和重建仓库新增功能分别标记，不混称为原产品固有能力。

先实际运行客户端，逐页记录入口、布局、默认状态、点击和键盘行为、加载反馈、成功结果、失败恢复、后台执行与返回页面后的状态。功能文件存在不代表流程已恢复，演示画面也不代表真实后端可用。

每项能力建立如下对照记录：

| 字段 | 内容 |
| --- | --- |
| 功能编号与名称 | 稳定标识及用户目的 |
| 来源与证据 | 原版或重建扩展、版本、截图或操作记录、源码位置 |
| 完整流程 | 触发条件、输入、执行、结果、异常及恢复 |

| 服务依赖 | Codex、Omega 服务、桌面系统能力或其他服务 |

## 4. 实现原则

### 客户端按产品重新组织

重新建立导航、页面结构、组件体系、交互状态和样式规范。桌面以已验证的 Grok Bot 布局与操作为主要依据；移动端将侧栏和信息面板转换为可操作的抽屉或浮层，避免机械缩放桌面界面。

保留 Omega 名称、标识和独立产品身份。基础样式与交互成套实现，避免各页面继续采用不同的临时按钮、弹窗和状态规则。

### 源码复用服务于产品结果

- 可读、可构建且行为完整的模块优先直接迁移。
- 依赖原协议或 Electron 的模块，保留适用界面和逻辑，替换接口边界。
- 缺失或不完整的源码，依据实际操作证据重新实现。
- 依赖原服务的功能，补充 Omega 服务或对应执行环境。

不要求所有功能从零写，也不为了保持当前 Omega 文件结构阻碍整块迁移。记录代码和资源来源，保留适用声明，核对纳入工程的使用条件。原压缩产物作为调查参考，不作为长期业务源码基础。

### 已有实现按价值保留

已有认证、图片管理、会话接入、群组持久化、调度和历史分页可以继续使用，也允许为完整流程调整接口和内部结构。服务端不是冻结不动的约束。

### 已确定的技术栈

以下为用户已确认的选型，不再作为 Tauri 与 Electron 二选一的待决事项：

| 层面 | 确定方案 |
| --- | --- |
| 共享前端 | React + TypeScript，统一组件、状态和业务接口 |
| Omega 服务端 | Node.js + TypeScript；业务实现已迁入 `.ts` 严格检查，旧 `.mjs` 仅保留无业务逻辑的兼容入口 |
| Windows / macOS 桌面端 | Electron，主进程与 preload 同样使用 TypeScript |
| Web | 运行共享前端，通过网络连接 Omega 服务端 |
| Android | 延续现有 Tauri Android 外壳作为迁移起点，加载共享前端并保留移动端桥接 |
| 核心执行系统 | Codex App Server，保持独立，不在本项目中改写其实现语言 |
| 持久化 | 沿用现有 SQLite 和文件数据，语言迁移不意味着更换数据库 |

Electron 用于桌面端，Android 不使用 Electron。Android 延续现有外壳是本计划的实施默认，不新增一次无关的移动端框架重写；后续确需调整时单独说明依据。

共享前端通过统一平台接口访问文件、剪贴板、外链、通知和凭据。Electron、Android、Web 分别实现平台接口，组件中不直接依赖 Electron 或 Tauri。各端共用业务与视觉代码，不要求共用同一个原生外壳。

### 后端 TypeScript 迁移要求

- 将 HTTP 接口、事件推送、Codex 桥接、群组存储与调度、附件、模型设置、用量统计等业务模块迁移到 TypeScript。
- 启用严格类型检查；建立请求、响应、消息、任务状态与事件契约，前后端共享不含服务器私有实现的类型包。
- 外部输入仍需运行时校验，不能以 TypeScript 类型代替网络请求、配置和数据库数据的验证。
- 按模块逐步迁移，允许过渡期新旧模块共存，避免一次性改写所有业务行为。完成标准包含服务端业务代码迁移及构建、启动、测试脚本同步调整。
- 保留会话 ID、数据库数据、任务去重和恢复语义；迁移前后使用相同契约与调度测试验证。
- 共享类型必须经独立构建或明确导出，浏览器构建不得打入 Node.js、数据库、密钥或执行桥接代码。

### Electron 桌面职责

- 复用 Grok Bot 中适用的窗口、菜单、快捷键、托盘、通知及 preload 交互，统一改为 Omega 品牌与服务接口。
- 主进程处理原生能力和应用生命周期，渲染进程展示共享前端，通过范围明确的 preload 接口通信。
- 启用上下文隔离，渲染进程不开放 Node.js 访问；IPC 参数与来源经过校验，凭据由原生侧妥善保存。
- 默认连接统一 Omega 服务端，不因关闭桌面窗口而终止服务端任务，也不在每台设备自动启动独立代理系统。
- 增加 Windows/macOS 的开发、构建和安装包脚本。桌面切换通过验收后移除旧 Tauri 桌面入口，保留 Android 所需工程与资源。

## 5. 执行架构与职责

```text
Omega 共享 React + TypeScript 客户端
Web / Electron 桌面 / Tauri Android
                  │
       客户端业务接口与平台桥接
                  │
                  ▼
Omega Node.js + TypeScript 服务端
认证、同步、附件、群组、任务与事件
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
Codex App Server       按功能补充的服务
会话、上下文、模型执行   自动化、工具连接、电脑环境等
工具调用与审批         （按调查结果确定）
```

Codex App Server 是主要代理执行系统。重建仓库现有 Codex 路由调用直接 Responses 接口，不能直接当作本方案需要的 App Server 接入。

协议转换属于内部实现。用户连接 Omega 后进入统一产品，不需要额外操作 Grok Bot 管理界面或重复创建同一套会话。工具连接和电脑环境接入前明确调用归属，避免同一任务由两套代理循环重复执行。

## 6. 必须保留的 Omega 工作方式

以下为用户明确要求，即使参照产品行为不同，也作为 Omega 的产品约束保留。

### 多端持续办公

- 所有设备连接同一服务端，共享权威会话、群组与执行状态。
- 关闭页面或 App 不终止服务端任务，重连后恢复结果和进度。
- 保留已有 Codex 会话 ID、上下文与项目文件，不能以新建空会话冒充迁移成功。
- 会话目录属于服务器，本机附件路径与服务器项目路径在逻辑上分清楚。
- 兼容当前 HTTP/FRP 连接方式，验证超时、断线和重连。

### 群组就是工作聊天室

- 每个成员是拥有自己上下文、身份、职责与工作目录的会话实体。
- 一个群组可协调多个项目，一个项目也可有多个成员会话。
- 明确 `@成员` 时直接派给该成员；未指定时按职责分配，多个问题可拆给不同成员。
- 派发内容简洁，优先传递用户问题和必要依赖结果，不反复注入背景身份或发散需求。
- 允许连续提问和多个需求排队，挑选依赖满足、成员空闲、目录不冲突的任务执行。
- 保留可设置并发、只读共享目录与写入冲突控制。
- 成员进度和答复直接进入群聊；问题栏用于定位、查看状态和时长。
- 用户通过追问、决策及必要审批推进工作，无需逐条点击验收通过。

### 轻量记录与历史性能

- 群组记录消息、目标摘要、任务分配和结果；成员保留自己的会话上下文。
- 不引入未经需求证明的复杂记忆系统，不把全部成员历史反复拼入提示词。
- 单聊和群聊历史按需加载，消息与缓存有上限，支持按问题直接定位。
- 最新消息增量更新，阅读历史时保持位置，避免节点和内存随翻页无限增长。
- 图片沿用超过 7 天自动清理，过期附件提供明确提示。

## 7. 业务契约与可靠性

定义会话、轮次、消息、任务、成员、附件、审批和平台接口，保留原始服务端标识，保障引用、定位和多端一致性。客户端需要的流程先明确，再对应现有接口，缺失能力补齐。

消息展示区分用户输入、助手回复、公开进度、工具调用、审批、错误与结束状态。使用服务端实际提供的数据，缺少 token 或时长时不编造数值。

发送区分提交中、已接收、排队、执行中、已回复与失败。建立请求标识与去重规则，网络超时后核对接收状态，避免重复执行。流式输出按消息 ID 合并，最终结果校准，重连补齐遗漏。

服务端保持数据权威；客户端负责有限缓存、布局偏好与草稿。共享数据和设备偏好分别定义同步范围，首版草稿默认本地保存。已有群组数据或会话关系需要迁移时，先验证迁移和恢复路径。

## 8. 实施阶段与交付物

### 阶段一：产品基线与工程迁移设计

运行参照客户端，完成页面地图、操作记录、功能对照表、源码完整度和服务依赖盘点。区分原版、重建扩展与 Omega 专属需求，核实打包路径和实际运行结果。按已确定的 React/TypeScript、Node.js/TypeScript 和 Electron 选型，明确共享契约、平台桥接、后端模块迁移顺序及复用范围。

交付：可逐项验收的完整产品规格、界面证据、工程结构、迁移清单和阶段范围。下一阶段依据规格实现，不用目录名猜测产品功能。

### 阶段二：完整客户端骨架

建立统一页面、导航、组件、样式和交互状态，覆盖主窗口、侧栏、聊天区、输入器、信息面板和设置。迁移适用源码、补齐缺失实现，用固定样本验证正常、空白、加载、错误及长内容状态，同时接入首条真实会话链路。

建立 Electron 主进程、preload 和共享前端工程；打通 Web 与 Electron 的平台接口。建立后端 TypeScript 构建、共享契约及类型检查，优先迁移支撑首条会话链路的模块。

交付：可以与参照产品逐页对照的 Omega 客户端骨架。样本和模拟能力明确标记，不能作为真实功能验收。

### 阶段三：真实可用核心版

接通已有会话、发送、停止、流式输出、工具卡片、审批、附件、模型设置和历史定位；完成群组成员、直接提及、队列、并发、回复关联和问题定位。补齐服务契约，验证持续工作、断线恢复与多端状态。

完成核心服务端业务模块的 TypeScript 迁移，更新开发、生产启动和测试脚本；验证现有数据与运行行为。新增扩展服务同样采用 TypeScript。

交付：能够完成真实单聊和群组工作的核心版，不仅是视觉原型。

### 阶段四：补齐完整功能

按清单实现搜索、快捷操作、原生集成，以及已核实的自动化、插件、电脑操作等扩展能力。需要后端或执行环境的功能同时交付服务，不能只保留没有作用的按钮。

交付：完整复刻清单逐项关闭；外部依赖明确列出阻塞条件与产品影响。调整已确认的目标范围需明确记录，不能用隐藏入口替代实现完成。

### 阶段五：多平台验收与切换

桌面参照体验优先建立，从阶段二开始持续验证手机布局；本阶段完成四个平台的构建和实际使用验证，处理安全区域、键盘、返回操作、文件选择和通知差异。

核心版可以先独立交付，不必等所有扩展功能。默认入口切换以该版本验收为前提，保留短期回退入口，再根据使用结果退出旧页面。完整复刻完成另行依据全清单判断。

交付：安装包、版本及功能范围说明、平台验证、已知差异和回退办法。前端资源打包成功不等于 App 实机验证完成。

## 9. 验收方式

每项功能同时检查界面、交互和实际结果，不能只凭截图或单元测试通过。

| 维度 | 验收标准 |
| --- | --- |
| 产品结构 | 页面分区、导航关系和主要信息层次对齐参照；差异有理由 |
| 操作体验 | 高频流程、快捷键、焦点、反馈、取消与失败恢复完整 |
| 功能真实性 | 从入口到后端执行及结果回显闭环，无仅展示的假功能 |
| 已有上下文 | 原会话 ID、上下文与工作目录保留，可继续工作 |
| 群组 | 连续提问、指定成员、跨目录并发和公开回复符合第六节 |
| 多端 | 一端发送，另一端看到进度与结果，重连不重复执行 |
| 长历史 | 固定样本下缓存和节点受控，切换和翻页后内存不持续攀升 |
| 手机 | 按钮可达，侧栏内容可见，系统栏和键盘不遮挡操作 |
| 桌面 | 布局、快捷键、文件和外链在目标平台实际可用 |
| 技术栈迁移 | 前后端及 Electron 严格类型检查通过，服务端生产构建和启动可用，核心业务无未完成的旧语言迁移项 |
| 平台隔离 | Web 不依赖 Electron/Tauri 全局对象，Android 桥接可用，Electron 原生接口通过 preload 暴露 |
| 完成范围 | 核心版与完整复刻分别列出已通过、延期和未验证项目 |

阶段一建立固定长会话、群聊和长工具输出样本，记录设备、内存、DOM 数、输入响应及更新耗时，确定性能预算。后续沿用相同样本比较，不能假设更换框架自然解决性能问题。

## 10. 工程边界与进度管理

- 当前已开始产品实现；实际完成度以同目录的 `product-parity.md` 为准，计划目标不因首个核心版本可运行而自动关闭。
- 后续允许重建客户端及调整服务端，保留用户已有会话和项目数据。
- 完成度以用户可用的功能清单与证据衡量，不以源码迁移比例衡量。
- 复杂后端能力先调查依赖，再分阶段交付，不因当前接口缺失永久排除。
- 持续推进可独立完成的工作；缺少外部账号、执行环境或付费服务时，列出具体缺口和影响。
- 只有逐项通过验收或明确调整目标范围后，才能宣告完整复刻完成。

当前实施入口是阶段二与阶段三并行收敛：继续把现有聊天主体迁移为 React 组件，将剩余服务模块迁移为 TypeScript，同时依据功能证据补齐桌面原生能力和完整复刻项。
