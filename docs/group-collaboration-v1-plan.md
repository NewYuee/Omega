# Omega 群组协作 V1 计划书

状态：V1 代码已实现并通过自动化测试，待使用真实会话完成两次端到端验收。

版本方向：轻量协作版，以“群组摘要 + 任务清单 + 结果交接”代替复杂的共享记忆系统。

当前实现落点：群组记录保存于 `.omega/omega.sqlite`；服务端调度器位于 `group-orchestrator.mjs`；Web、Electron 桌面端与 Tauri 移动端共用 `public/groups.js` 群组工作台。默认限制为同时 3 个任务、每张计划最多 8 个任务、2 次返工、12 个调度轮数和单任务 45 分钟。尚未用用户的正式项目执行本文末尾要求的真实验收，因此自动化测试通过不等同于业务验收通过。

## 一、目标

让用户在群组中提出需求后，Omega 能组织已有会话成员完成：

**明确需求 → 拆解任务 → 分配与调度 → 执行与交接 → 测试与返工 → 汇总交付 → 人工验收。**

第一版的成功标准不是多个会话可以互相聊天，而是：每个任务有人负责、执行过程可追踪、失败能够处理、结果有证据，并能由用户确认验收。

不承诺所有需求都能自动完成。遇到权限不足、需求不明确或达到执行限制时，必须暂停并明确报告原因，不能虚报完成。

第一版优先验证已有会话能否在协调者组织下完成交付，不建设独立知识库、向量检索或专职记录角色。信息管理保持简单，防重复执行、审批和验收等可靠性约束不能省略。

## 二、核心对象与职责

| 对象 | 职责 |
| --- | --- |
| 群组 | 保存成员、群组摘要、原始群消息、任务和交付历史 |
| 群组协调者 | 维护群组摘要、明确角色目标、拆分和分配任务、收取结果、处理返工、汇总交付 |
| 会话成员 | 保留自己的上下文，按照群内身份执行具体任务 |
| 需求单 | 用户在群里提出的一次需要交付的工作 |
| 任务 | 可以明确分配、执行和验证的工作单元 |
| 交付记录 | 记录完成了什么、产物在哪里、如何验证、还有什么问题 |

协调者负责作判断，服务端调度器负责控制执行。模型不能自行跳过审批、解除占用锁或修改执行预算。

协调者负责维护摘要并向成员传递必要背景，成员负责返回结构化结果，服务端负责持久化原始消息、交付结果和调度状态。成员不需要直接访问数据库或操作一套独立记忆系统。

## 三、第一版使用流程

### 3.1 创建群组

创建时填写：

- 群组名称、项目说明。
- 项目级约束。
- 执行限制，例如任务数量、返工次数、最长执行时间。

为群组创建一个只负责计划和审核的专用协调者会话。群组本身不绑定项目目录；用户可以连续提交多张需求单，形成持久化队列。

### 3.2 添加已有会话

从现有会话列表中选择成员，并设置：

- 身份名称，例如设计、开发、测试。
- 职责范围。
- 允许的操作范围。
- 擅长处理的任务类型。
- 项目名称；成员的实际工作目录直接取自其原会话。

成员继续使用原会话，保留原有上下文。群组身份作为本次任务的补充要求，不覆盖原会话的全局配置。

第一版约束：

- 一个执行会话只能绑定一个群组。
- 会话忙碌时，不能同时接收群任务和个人窗口的新任务。
- 退出群组不删除会话和历史。
- 正在执行任务的成员不能直接移除。

### 3.3 提交需求

示例：

> 给 Omega 增加消息搜索，手机和电脑都能使用，并提供测试结果。

协调者先整理：

- 要实现什么。
- 不包含什么。
- 有哪些约束。
- 什么结果算通过验收。
- 是否有必须向用户确认的问题。

关键信息不足时进入“等待补充”，不能靠猜测继续扩大任务范围。

### 3.4 制定并确认计划

协调者生成结构化任务计划，例如：

| 任务 | 负责人 | 前置条件 | 交付要求 |
| --- | --- | --- | --- |
| 整理搜索交互方案 | 设计成员 | 需求已确认 | 交互说明、边界情况 |
| 实现搜索功能 | 开发成员 | 方案通过 | 代码改动、使用说明 |
| 验证功能 | 测试成员 | 实现完成 | 测试结果、问题清单 |
| 汇总交付 | 协调者 | 验证通过 | 交付报告、验收步骤 |

服务端检查任务负责人、依赖关系和执行限制是否合法。

第一版默认由用户确认计划后开始执行。用户可以修改分工、范围和验收条件，也可以取消。

流程不强制所有需求都经过设计、开发、测试三个角色。协调者根据真实依赖形成任务图；无依赖且资源不冲突的任务允许并行。

### 3.5 调度与执行

任务满足以下条件才允许启动：

- 计划已确认。
- 前置任务已经通过。
- 成员会话空闲。
- 工作目录没有冲突中的写入任务。
- 没有阻止本任务执行的待处理审批。
- 未超过执行限制。

每次派发包含：

**成员原上下文 + 群内职责 + 当前目标与相关约束 + 前置任务结果 + 本次任务及验收要求。**

成员原上下文通过继续使用原会话保留，不复制全部历史。协调者从群组摘要和交付记录中选取本次所需信息，附在任务里；成员发现信息不足时，向协调者请求补充，由协调者查阅原始消息或相关交付记录后回复。

执行期间，群组展示关键进展；详细命令、工具输出和消息仍保留在成员会话里，点击后按需查看。

### 3.6 验证与返工

成员执行结束后先进入“待验证”，不能直接判定任务通过。

交接记录必须包含：

- 完成内容。
- 产物位置、修改文件或差异。
- 验证方式和实际结果。
- 未完成事项、风险及阻塞原因。
- 对应会话和执行轮次的引用。

测试未通过时，形成具体问题并退回负责人。返工必须记录原因，受最大次数限制，不能无限循环。

服务端保存成员返回的交付正文及会话、轮次引用；协调者据此更新群组摘要，并将必要结果交接给下一个角色。不能只保存协调者对成员结果的二次摘要。

### 3.7 交付与验收

所有必要任务通过后，协调者生成统一交付报告：

- 原始需求与验收条件。
- 实现结果。
- 文件、文档或其他产物入口。
- 测试证据。
- 验收操作步骤。
- 已知限制和未解决问题。

需求单进入“待用户验收”。用户可以选择：

- **验收通过**：标记为已完成。
- **要求修改**：带着具体意见进入返工。
- **终止需求**：保留已有成果和执行记录。

模型宣布完成，不等于用户已经验收。

## 四、轻量上下文与记录方案

成员继续保留自己的会话上下文；群组只维护协作所需的三类记录，不建立独立知识库。

### 4.1 三类核心记录

| 记录 | 内容 | 维护责任 |
| --- | --- | --- |
| 群组摘要 | 当前目标、用户约束、已确认决策、整体进度、待确认问题 | 协调者整理，服务端保存 |
| 任务清单 | 负责人、任务目标、前置条件、执行状态、验收要求 | 协调者提出计划，服务端校验并管理执行状态 |
| 交付记录 | 成员返回的结果正文、产物位置、验证情况、遗留问题、会话与轮次引用 | 成员提交，服务端保存，协调者负责交接 |

摘要用于帮助协调者快速理解现状，不作为事实和执行状态的唯一依据。任务是否已派发、正在执行、等待审批或已经通过，以服务端保存的任务记录为准，不能只写在摘要或协调者上下文里。

### 4.2 最小存储方案

使用一个 SQLite 数据库保存：

- 群组、成员、需求单和已确认计划。
- 当前群组摘要及其覆盖的消息位置。
- 用户原始群消息和成员交付结果。
- 任务、依赖、唯一派发标识、关联会话与轮次、执行状态。
- 必要的审批、返工和最终验收记录。

代码、设计文件和测试报告等产物继续保存在项目目录，数据库只保存必要的路径或引用；代码仍由 Git 管理。第一版不额外维护一套文件记忆，不要求导出或同步独立的项目记忆文档。

摘要保存覆盖的消息位置，是为了在恢复时识别尚未整理的新消息；不建设通用知识条目、复杂修订历史或自动冲突消解系统。

### 4.3 协调者的记录与交接流程

1. 收到用户需求或补充意见时，服务端先保存原文。
2. 协调者整理目标、约束和验收要求，更新群组摘要与任务计划。
3. 派发任务时，附上角色职责、相关背景、前置结果和明确交付要求。
4. 成员继续在原会话中执行；缺少信息时请求协调者补充，不默认读取全部群消息或其他成员历史。
5. 服务端保存成员返回的结果，协调者判断下一步：交给下一角色、要求返工、等待用户补充，或汇总交付。
6. 协调者更新摘要；如果它的上下文被压缩或会话需要恢复，重新读取当前摘要、任务清单，以及摘要未覆盖的消息和必要交付记录。

成员的原上下文不会因此被清空，也不会自动共享给其他成员。已有会话中的旧背景确实需要共享时，由成员返回相关说明，协调者再交接给需要该信息的角色。

### 4.4 避免摘要丢失关键细节

- 用户原始要求和成员交付正文保留，不能被摘要替代或覆盖。
- 摘要中的关键约束和结论附上相应消息或交付记录引用，细节不清楚时回看原文。
- 明确区分“用户已确认”“成员建议”和“待确认”，不把推测写成事实。
- 发现需求或结论冲突时，记录问题并向用户确认，不自动解决语义冲突，也不静默覆盖已确认计划。
- 更新摘要失败时保留原始记录，并在下次调度前补齐所需信息，不能假定未处理的新要求已经生效。
- 群组记录属于项目，不依赖某个协调者会话永久保留完整上下文。

### 4.5 保留策略边界

图片继续遵守现有七天清理规则。第一版不静默延长保存期限，过期引用必须明确显示失效。

不能仅凭保存了引用，就声称原始依据可以永久读取。重要依据的额外归档策略需要单独确认。

## 五、调度可靠性与安全边界

### 5.1 防止重复执行

每次任务派发保存唯一标识和执行记录。

服务重启后先核对已有会话和轮次：

- 能确认结果的，恢复状态。
- 无法确认是否执行过的，进入“待核对”。
- 不直接重新发送可能已执行过的操作。

### 5.2 防止工作目录冲突

第一版允许跨项目并行执行，并为任务建立工作目录占用机制。调度器每次从所有已确认需求中选择依赖满足、成员空闲、目录不冲突的任务，直到达到群组并发上限。

同时检查：

- 其他群组的写入任务。
- 个人窗口发起的任务。
- 相同目录及重叠的父子目录。

锁必须由服务端统一执行，而不是仅在前端禁用按钮。它不能阻止 Omega 之外的终端或其他软件修改文件，这项边界需要明确提示。

### 5.3 权限与审批

角色描述不等于权限控制。

实施前需要验证现有 App Server 能否可靠限制对应工具和写入权限；不能可靠限制的能力，第一版不开放自动执行。

默认不自动进行下列操作，必须获得对应授权：

- 删除已有会话或项目文件。
- 提交、推送、合并代码。
- 发布、部署服务。
- 安装需要额外授权的软件。
- 扩大工作目录或外部服务访问范围。

已有审批继续由用户处理，协调者不能代替用户批准。

### 5.4 执行限制

至少支持：

- 最大任务数。
- 最大返工次数。
- 单次执行超时。
- 最大调度轮数。
- 可获取准确用量时的 token 限额。

若供应商没有返回完整用量，不能把 token 预算当作精确硬限制；仍须依靠次数、时间等限制停止失控执行。

## 六、第一版功能范围

### 6.1 包含

- 创建、查看群组，管理会话成员与角色。
- 群组专用协调者。
- 需求整理、结构化计划、人工确认。
- 多需求队列，以及按依赖、成员和目录锁进行的条件并行调度。
- 会话占用与工作目录冲突检查。
- 群组摘要维护，原始群消息与成员交付结果留存。
- 协调者按任务传递必要背景，成员缺信息时请求补充。
- 任务交接、验证、有限返工。
- 人工审批、暂停后续调度、中断当前执行。
- 交付报告和人工验收。
- 多设备同步状态与按需查看详情。
- 重启恢复和未知结果处理。

### 6.2 暂不包含

- 多个开发成员并行修改同一项目。
- 自动创建和合并多个 Git worktree。
- 一个执行会话同时加入多个群组。
- 成员无限制自由讨论、互相派活。
- 跨群组自动共享记录。
- 独立知识库、向量检索、语义搜索和自动记忆分层。
- 通用知识条目版本管理、自动冲突消解或独立文件记忆同步。
- 成员直接操作 SQL 或自行维护共享记忆。
- 自动部署、自动发布。
- 独立的专职记录员。

## 七、实施顺序

### 阶段 A：验证底层能力

检查现有代码和 App Server 协议，验证：

- 原会话能否可靠恢复并执行群任务。
- 单会话占用和运行状态如何判断。
- 任务结束、失败、中断如何识别。
- 审批如何关联回群组任务。
- 角色权限和工作目录限制如何落实。
- 服务重启后如何核对执行结果。

先用隔离测试会话验证，不拿用户的日常会话试验破坏性操作。

**产出：技术接入方案和已确认的限制。**

### 阶段 B：建立协作基础

实现最小 SQLite 存储、群组成员、群组摘要、原始群消息、任务清单和派发记录。

**产出：可以可靠保存和恢复的轻量协作记录，不包含独立记忆系统。**

### 阶段 C：跑通执行闭环

实现计划确认、依赖调度、协调者传递背景、成员执行、结果保存与交接、验证和返工。

**产出：不依赖完整界面，也能让多张需求排队并并行推进可运行任务。**

### 阶段 D：接入客户端

提供群组入口、需求计划、任务进度、审批和交付查看功能。详细交互方案单独确认，沿用当前 Omega 风格。

**产出：Web、Electron 桌面端和 Tauri 移动端共用的群组协作界面。**

### 阶段 E：可靠性验收

验证断线、重启、并发操作、审批等待、任务失败、返工超限和成员会话占用。

**产出：测试报告、使用说明和已知限制。**

## 八、第一版验收标准

| 场景 | 必须达到的结果 |
| --- | --- |
| 正常需求 | 经用户确认计划后，按分工完成并生成可检查的交付报告 |
| 沿用已有会话 | 继续使用原会话，不删除历史，不覆盖全局身份 |
| 前置任务未完成 | 下游任务不能提前执行 |
| 成员正在忙碌 | 任务等待，不向同一会话并发派发 |
| 工作目录冲突 | 阻止重叠写入，明确提示占用原因 |
| 成员声称完成但无证据 | 不能直接进入最终验收 |
| 测试发现问题 | 有明确返工任务，保留失败和修复记录 |
| 返工达到上限 | 停止自动推进，向用户报告 |
| 执行中补充需求 | 记录为计划变更，确认后生效，不静默改写正在执行的任务 |
| 客户端关闭或断线 | 不因窗口关闭而停止服务端调度 |
| 服务端重启 | 恢复记录，不盲目重复执行未知结果的任务 |
| 多设备操作 | 状态一致，重复确认或审批不会重复执行 |
| 摘要缺少关键细节 | 能通过引用找到用户原始要求或成员交付正文，不依赖再次猜测 |
| 协调者上下文被压缩或恢复 | 能从群组摘要、任务清单和必要原始记录继续推进 |
| 成员缺少背景 | 能向协调者请求补充，再接收与当前任务相关的信息 |
| 摘要与原文或已确认计划不一致 | 以原始依据和已确认计划核对，涉及变更时由用户确认，不静默覆盖 |
| 摘要更新失败 | 原始消息和交付结果仍被保存，后续调度不能漏掉未处理的新要求 |
| 最终交付 | 用户能打开产物、按步骤验证，并明确接受或退回 |

第一版使用隔离的演示项目完成两次端到端验收：

1. 一次正常交付。
2. 一次包含测试失败和返工的交付。

两种流程都跑通后，再用于正式项目。

## 九、实施前待确认事项

- 详细的数据模型、任务状态机和接口契约，在阶段 A 完成后确定。
- 默认任务数量、时间、返工次数及用量限制，需要给出具体数值并确认。
- 角色权限的实际执行方式，以底层能力验证结果为准。
- 群组摘要的长度上限、更新时机和原始记录保留策略，需要明确；图片默认仍为七天。
- 详细交互设计单独确认，不在计划书落盘阶段修改界面。

本计划的重点：用轻量共享摘要、可靠任务调度和可追溯交付，先让一组已有会话稳定完成一件事。只有实际使用证明摘要与交接不足时，再考虑扩展记忆能力、并行度和自主性。
