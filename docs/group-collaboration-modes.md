# 群组协作模式

每次发送前，在群组输入框上方选择本次提问的模式。发送成功后恢复“直接处理”，避免后续普通问题意外进入协作。

- **直接处理**：默认模式。`@成员` 直接派发，引用追问继续交给原成员；没有指定成员时由协调者选负责人。
- **允许交接**：当前成员完成工作后，可以提出结构化交接请求，指向群内其他成员。后续任务沿用接收成员自己的目录和上下文，并接收前置结果。普通回复中的 `@` 不会触发交接。
- **讨论（只读）**：指定多个成员参与，未指定时由全体成员参与。每轮参与者可以并行回复；所有人完成后才进入下一轮，补充不同意见和新事实。全员无补充时提前结束。讨论不执行代码修改或发布。

交接默认 10 轮，讨论默认 3 轮；两种模式都允许输入 1–100 的整数。首轮也计入上限，交接按任务链的深度计轮次。到限时保留后续排队任务，调整总预算后可以继续，不重复执行已完成的任务。单问题保留 3000 个任务的防失控上限。原有并发数和目录冲突控制继续生效。时间、Token 预算和详细边界见 [日用说明](group-daily-use.md)。

聊天中显示成员处理轮次，交接对象与目标直接记入消息。进度详情默认折叠，正式答复与决策表单直接展示。原提问旁和正在处理提示中的“停止协作”会取消尚未完成的工作，并尝试中断当前执行；已发生的文件修改不会自动回滚。

成员交接协议（仅允许交接模式生效）：

```text
<omega-handoff>{"tasks":[{"memberId":"群内成员 ID","objective":"必要的后续工作"}]}</omega-handoff>
```

单次最多交接 3 人，不能指向自己、重复对象或群外成员。交接创建与当前结果保存处于同一数据库事务，服务恢复采用相同完成入口，防止重复接续。讨论无补充使用 `(pass)`，不在聊天中新增空洞答复。

如需用户决定，现有决策表单优先处理；用户提交选择后，该成员继续执行，再决定是否交接。
